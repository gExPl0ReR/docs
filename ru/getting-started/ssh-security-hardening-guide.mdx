Усиливайте защиту SSH поэтапно: сначала настройте рабочий аккаунт администратора и SSH-ключ, затем ограничьте способы входа. Команды ниже предназначены для **Debian и Ubuntu**.

<Warning>
  Оставьте текущий SSH-сеанс открытым и обеспечьте доступ к [консоли VNC](/ru/vps-management/enable-vnc-server). После каждого изменения проверяйте второй независимый вход. Не отключайте единственный работающий способ доступа.
</Warning>

## 1. Обновите OpenSSH {#1-update-openssh}

Используйте пакеты своего дистрибутива: исправления безопасности могут переноситься в них без изменения номера основной версии. Следуйте руководству [Обновление SSHD](/ru/advanced-setup-guides/security-advisories/update-sshd-debian-ubuntu-redhat).

## 2. Создайте и проверьте аккаунт администратора {#2-create-and-test-an-administrator-account}

На VPS создайте аккаунт, если его ещё нет. Во всём руководстве заменяйте `adminuser` на выбранное имя пользователя:

```bash
sudo adduser adminuser
sudo usermod -aG sudo adminuser
```

В **новом терминале на своём компьютере** подключитесь как этот пользователь и проверьте административный доступ:

```bash
ssh adminuser@YOUR_VPS_IP
sudo -v
```

Оставьте исходный сеанс открытым, пока обе команды не выполнятся успешно.

## 3. Настройте аутентификацию по SSH-ключу {#3-configure-ssh-key-authentication}

На **своём компьютере** создайте ключ, если его ещё нет. Защитите его парольной фразой и не перезаписывайте существующий ключ, которым ещё пользуетесь:

```bash
ssh-keygen -t ed25519
ssh-copy-id adminuser@YOUR_VPS_IP
```

`ssh-copy-id` копирует публичный ключ; приватный ключ должен оставаться на вашем компьютере. Если клиент не содержит этого инструмента, следуйте его инструкциям по установке публичного ключа. См. [руководство OpenSSH по созданию ключей](https://man.openbsd.org/ssh-keygen).

Проверьте новое подключение, разрешающее **только аутентификацию по публичному ключу**:

```bash
ssh -o PreferredAuthentications=publickey -o PasswordAuthentication=no adminuser@YOUR_VPS_IP
```

Запрос парольной фразы приватного ключа — нормальное поведение. Убедитесь, что `sudo -v` также работает в новом сеансе.

## 4. Ограничьте способы входа {#4-restrict-login-methods}

Сделайте резервную копию `/etc/ssh/sshd_config` и файлов в `/etc/ssh/sshd_config.d/`, которые будете редактировать. Прежде чем добавлять настройки, изучите существующую конфигурацию: подключаемые фрагменты могут иметь приоритет над основным файлом.

Для **входа только по ключу без MFA на основе PAM** задайте:

```text
PubkeyAuthentication yes
PasswordAuthentication no
KbdInteractiveAuthentication no
PermitRootLogin no
```

Делайте это только после проверки входа по ключу под администратором, отличным от root. Эти настройки не отключают пароль аккаунта для входа через консоль или использования `sudo`.

Проверьте синтаксис и фактически применяемую конфигурацию:

```bash
sudo /usr/sbin/sshd -t
sudo /usr/sbin/sshd -T | grep -E '^(pubkeyauthentication|passwordauthentication|kbdinteractiveauthentication|permitrootlogin) '
```

Если используются блоки `Match`, настройки могут различаться в зависимости от пользователя и подключения. Прежде чем продолжить, устраните неожиданные значения. OpenSSH обычно использует первое найденное значение каждого параметра; см. [руководство Ubuntu по настройке OpenSSH](https://ubuntu.com/server/docs/how-to/security/openssh-server/) и [справочник конфигурации OpenSSH](https://man.openbsd.org/sshd_config).

Если проверка прошла успешно, перечитайте конфигурацию SSH в Debian/Ubuntu:

```bash
sudo systemctl reload ssh
```

Откройте ещё одно новое подключение и проверьте вход по ключу и `sudo`, прежде чем закрывать исходный сеанс.

## 5. Добавьте правила до включения межсетевого экрана {#5-apply-firewall-rules-before-enabling-the-firewall}

Разрешите **фактический TCP-порт SSH** до включения UFW. По умолчанию это порт 22; замените его, если меняли. Следуйте [руководству по UFW](/ru/advanced-setup-guides/ufw-uncomplicated-firewall-howto), включая проверку повторного подключения.

Нестандартный порт может уменьшить количество автоматических попыток входа, но не заменяет аутентификацию или контроль доступа. Смена порта также требует согласованных настроек межсетевого экрана, клиента и иногда `ssh.socket`. Она необязательна и не входит в описанную выше процедуру настройки входа только по ключу.

## 6. Контролируйте доступ и рассмотрите дополнительные меры {#6-monitor-access-and-consider-additional-controls}

Просмотрите недавние события SSH в Debian/Ubuntu:

```bash
sudo journalctl -u ssh --since '1 hour ago'
```

Fail2Ban может временно блокировать повторные неудачные попытки входа. Настройте порт SSH и источник журналов в соответствии с сервером; не считайте, что `/var/log/auth.log` обязательно существует в системе, использующей только journal.

Для MFA следуйте полной процедуре своего дистрибутива и провайдера аутентификации. Одно лишь включение keyboard-interactive **не** делает второй фактор обязательным. Настройка MFA должна объединять нужные методы и охватывать всех затронутых пользователей; она также отличается от приведённой выше схемы входа только по ключу. См. [OpenSSH AuthenticationMethods](https://man.openbsd.org/sshd_config#AuthenticationMethods).

## Если новый вход не работает {#if-a-new-login-fails}

Оставьте существующий сеанс открытым, проверьте журнал SSH и восстановите изменённые файлы конфигурации. Перед перечитыванием настроек выполните проверку `sshd -t`. Если весь доступ по SSH потерян, исправьте конфигурацию через [консоль VNC](/ru/vps-management/enable-vnc-server).

## What is a rescue CD and why use it?

**SystemRescueCD** is a Linux-based live environment used for troubleshooting and maintenance. It allows you to:
- Access and repair non-booting systems  
- Check and fix disk, network, and firewall issues  
- Mount your main OS partitions and modify configurations  
- Recover access when SSH or firewall rules block connectivity  

---

## Mount and boot the SystemRescueCD

1. Log in to your [VPS Management Portal](https://manage.edisglobal.com/clientarea.php).  
2. From your VPS dashboard, click **Mount ISO**.  
3. In the ISO list, select **System-Rescue-CD-6-x86.iso**.  
4. Enable the **force reset & boot** option and click **Mount ISO** to start the process.  

   ![Mount ISO Dialog](/assets/Ijip8O_qmSgr6LR-nJvf5_sysrescuecd1.png)

5. Once mounted, click **Start VNC**, then **Open Console** to access the console.  
6. In the boot menu, select **Boot SystemRescueCd using default options** and press **Enter**.  

   ![noVNC Boot Screen](/assets/vg4lijwNdjgyOUDN05SQD_sysrescuecd2.png)

7. If it boots into a command-line interface, start the graphical desktop manually:

   ```bash
   startx
   ```

## Configure network in rescue mode

You can configure networking via the GUI (simplest) or command line.

### Using the graphical interface

1. Open **Settings → Advanced Network Configuration**.  
![Advanced Network Configuration](/assets/AdvancedNetworkConfiguration.png)

2. Select your wired interface (e.g., *Wired connection 1*).  

3. Click the **gear** ⚙️ icon to open settings.  
![Interface Settings (Gear)](/assets/InterfaceSettings(Gear).png)

4. **IPv4** tab → **Method: Manual** → **Add** your IP, Netmask, and **your actual Gateway**.  

5. **DNS**: e.g., `1.1.1.1, 1.0.0.1` → **Save**.  
![IPv4 Manual Settings/DNS](/assets/IPv4ManualSettingsandDNS.png)

You can find your assigned IP information at [VPS IP address settings](/vps-management/ip-address-information).

**Quick connectivity checks:**

~~~bash
ping -c 3 8.8.8.8
ping -c 3 1.1.1.1
ping -c 3 YOUR_GATEWAY   # replace with your real gateway
ping -c 3 google.com       # DNS + outbound test
~~~

### Using command line (if GUI not available)

If you’re in command-line mode:

~~~bash
ip a                            # identify the interface (eth0 / ens3)
ip addr add YOUR_IP/PREFIX_LENGTH dev eth0
ip route add default via YOUR_GATEWAY

echo "nameserver 1.1.1.1" > /etc/resolv.conf
echo "nameserver 8.8.8.8" >> /etc/resolv.conf

ping -c 4 8.8.8.8
ping -c 4 YOUR_GATEWAY
ping -c 4 google.com
~~~

<Note>

## Check the firewall from rescue mode

If you are in the graphical environment, open a **Terminal** first.

When the Rescue CD boots, its internal firewall (iptables or nftables) is usually disabled.  
To review or modify the firewall of your **main system**, follow these steps:

1. Identify and mount your main partition:
~~~bash
lsblk
mkdir -p /mnt/system
mount /dev/vda1 /mnt/system
# Replace /dev/vda1 with your actual root partition.
~~~

2. Check if UFW was enabled:
~~~bash
cat /mnt/system/etc/ufw/ufw.conf
# look for: ENABLED=yes
~~~

3. Inspect rules:
~~~bash
cat /mnt/system/etc/ufw/user.rules
# or, for iptables-persistent:
cat /mnt/system/etc/iptables/rules.v4
~~~

4. Back up any configuration file before editing it. Inspect both IPv4 and IPv6 rules (`user.rules` and `user6.rules` for UFW, or `rules.v4` and `rules.v6` for iptables-persistent).

The installed OS is not running while you are booted into rescue mode. `chroot` changes the filesystem view; it does not boot that OS or start its service manager. Running `systemctl stop` in a chroot therefore does not stop the installed system's firewall. Use the rescue environment to inspect and repair its **persistent files**, then boot the installed OS and verify the firewall from the VNC console. Avoid flushing rules or disabling protection as a generic fix.

## Check SSH configuration and service

If you are in the graphical environment, open a **Terminal** first.

When the Rescue CD boots, SSH is not automatically running since the main system isn’t active yet.  
To review or fix the SSH configuration of your **main system**, follow these steps:

To troubleshoot SSH from the Rescue environment:

1. Mount the main system partition if it is not already mounted from the firewall checks:
~~~bash
lsblk
mkdir -p /mnt/system
mount /dev/vda1 /mnt/system
# Replace /dev/vda1 with your actual root partition.
~~~

Verify it’s mounted correctly:
~~~bash
mount | grep /mnt/system
ls /mnt/system/etc/
~~~

2. Inspect SSH config:
~~~bash
cd /mnt/system/etc/ssh
cat sshd_config
ls -la sshd_config.d/
~~~

Read applicable configuration snippets as well as the main file; their settings can take precedence.

3. Inspect installed SSH unit files without trying to start the installed OS:
~~~bash
systemctl --root=/mnt/system list-unit-files 'ssh*'
~~~

Look for `ssh.service`, `sshd.service`, or `ssh.socket`, depending on the distribution. This reports unit-file configuration, not whether the installed OS is currently running. See [systemctl's offline root option](https://man7.org/linux/man-pages/man1/systemctl.1.html).

4. (Optional) Edit SSH settings:
~~~bash
nano /mnt/system/etc/ssh/sshd_config
~~~

5. Finish recovery and test the installed OS:

- Leave any shell whose working directory is inside `/mnt/system`, and unmount any filesystems you mounted. Do not force-unmount a busy filesystem; first close processes using it.
- [Unmount the rescue ISO](/vps-management/mount-iso-image), then reboot from the virtual disk.
- In the VNC console, check SSH syntax with `sudo /usr/sbin/sshd -t`, inspect the SSH service and firewall, and confirm the assigned network settings.
- From a terminal on **your own computer**, test the VPS's actual SSH port and attempt a fresh login:

~~~bash
nc -zv YOUR_VPS_IP 22
ssh username@YOUR_VPS_IP
~~~

Replace the placeholders and port. Testing while still booted into rescue mode only tests the rescue environment, not the installed system. Stop VNC after recovery is complete.

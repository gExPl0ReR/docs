RouterOS calls its IPv6-over-IPv4 tunnel interface **6to4**. With an explicit `remote-address`, you can use it for a configured point-to-point link between two routers. This routes IPv6 traffic; it does not bridge Ethernet or automatically provide public IPv6 Internet access.

This example uses private IPv6 networks behind two routers and RouterOS's `ipsec-secret` option. See the [MikroTik interface reference](https://manual.mikrotik.com/docs/cli-reference/interface/6to4/) for current behavior and IPsec defaults.

## Before you begin

- You administer both RouterOS routers and their firewall policies.
- Both ends have reachable public IPv4 addresses. This example does not cover NAT.
- Each router has an appropriate LAN interface or bridge for its downstream network. Do not blindly apply the LAN address to a VPS's public/WAN interface.
- Back up the router configuration and keep an alternate management connection available.

An EDIS VPS already has [native IPv6](/vps-management/ipv6-configuration). This tunnel is for a specific network design; it is not required to enable ordinary VPS IPv6 connectivity.

## Example address plan

All addresses below are **documentation examples**. Replace the IPv4 endpoints with your actual public addresses. For production private networks, generate a unique ULA `/48` prefix and allocate non-overlapping subnets; see [RFC 4193](https://www.rfc-editor.org/rfc/rfc4193.html).

| Setting | Router 1 | Router 2 |
| --- | --- | --- |
| Public IPv4 placeholder | `192.0.2.10` | `198.51.100.20` |
| Tunnel address | `fd42:ed15:1234:ffff::1/126` | `fd42:ed15:1234:ffff::2/126` |
| LAN subnet | `fd42:ed15:1234:1::/64` | `fd42:ed15:1234:2::/64` |
| LAN router address | `fd42:ed15:1234:1::1/64` | `fd42:ed15:1234:2::1/64` |

The ULA addresses are for private communication, not globally routed Internet addresses. Replace `LAN_INTERFACE` below with each router's actual downstream interface or bridge.

## 1. Enable IPv6

On both routers:

```text
/ipv6/settings/set disable-ipv6=no
```

![Enable IPv6 in RouterOS](/assets/enable-ipv6.png)

## 2. Create the tunnel

Use the **same long, randomly generated secret** at both ends. `REPLACE_WITH_UNIQUE_SECRET` is a placeholder, not a usable example password. Do not reuse a public documentation password.

On Router 1:

```text
/interface 6to4 add local-address=192.0.2.10 remote-address=198.51.100.20 mtu=1280 name=6to4-tunnel ipsec-secret="REPLACE_WITH_UNIQUE_SECRET"
```

On Router 2:

```text
/interface 6to4 add local-address=198.51.100.20 remote-address=192.0.2.10 mtu=1280 name=6to4-tunnel ipsec-secret="REPLACE_WITH_UNIQUE_SECRET"
```

Specifying `ipsec-secret` creates a dynamic IPsec peer and policy. Review the negotiated algorithms and policy against your requirements; creating the interface alone does not prove that encrypted traffic is flowing.

## 3. Assign the tunnel and LAN addresses

On Router 1:

```text
/ipv6/address/add address=fd42:ed15:1234:ffff::1/126 interface=6to4-tunnel advertise=no
/ipv6/address/add address=fd42:ed15:1234:1::1/64 interface=LAN_INTERFACE advertise=no
```

On Router 2:

```text
/ipv6/address/add address=fd42:ed15:1234:ffff::2/126 interface=6to4-tunnel advertise=no
/ipv6/address/add address=fd42:ed15:1234:2::1/64 interface=LAN_INTERFACE advertise=no
```

These examples do not configure downstream clients or router advertisements. Configure each client with an address from its LAN subnet and a route through its local router, or configure IPv6 address distribution separately.

## 4. Route the remote LAN

On Router 1:

```text
/ipv6/route/add dst-address=fd42:ed15:1234:2::/64 gateway=fd42:ed15:1234:ffff::2
```

On Router 2:

```text
/ipv6/route/add dst-address=fd42:ed15:1234:1::/64 gateway=fd42:ed15:1234:ffff::1
```

Permit the required IPsec negotiation and encrypted traffic between the two exact IPv4 peers, and the intended IPv6 forwarding between your LANs. Protocol 41 is an IP protocol number, not TCP or UDP port 41. Do not add a broad rule accepting unprotected encapsulated traffic as a shortcut around an IPsec policy problem.

## 5. Verify both routing and encryption

First check that the expected IPsec peer and security associations are established in RouterOS. Then test the remote tunnel endpoint and remote LAN router address.

From Router 1:

```text
/ping fd42:ed15:1234:ffff::2
/ping fd42:ed15:1234:2::1
```

From Router 2:

```text
/ping fd42:ed15:1234:ffff::1
/ping fd42:ed15:1234:1::1
```

Finally, test traffic between actual downstream hosts and inspect IPsec counters. A successful ping to a router alone does not verify downstream routing or the confidentiality of the path.

If a test fails, check endpoint reachability, the shared secret, IPsec policies, IPv6 routes, firewall counters, and the LAN clients' return routes. The starting MTU of `1280` may also need path-specific investigation; it is not a guarantee that every underlying path can carry the encapsulated packet without fragmentation.
